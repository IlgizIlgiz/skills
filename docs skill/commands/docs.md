# Documentation Organizer — /docs

Скилл для организации документации проекта. Разбивает CLAUDE.md на компактное ядро + детальные файлы в `docs/`.

## Входные данные

$ARGUMENTS

Если аргумент пустой — запускается полный цикл (анализ + реорганизация + верификация).
Если указан аргумент (например, "обнови api") — обновляется только указанная секция.

## Как работает

### Шаг 1: Определить текущее состояние

Прочитай `CLAUDE.md` в корне проекта.

**Вариант A — Структура уже организована** (есть теги `<!-- ESSENTIAL:START -->` и `<!-- ESSENTIAL:END -->`):
→ Перейти к Шагу 4 (верификация и обновление).

**Вариант B — Структура НЕ организована** (нет тегов):
→ Продолжить со Шага 2 (первичная организация).

### Шаг 2: Анализ и классификация (только при первом запуске)

Проанализируй весь контент CLAUDE.md и раздели его на две категории:

**ESSENTIAL (остаётся в CLAUDE.md)** — информация, которая нужна Claude при КАЖДОЙ новой сессии:
- Название и описание проекта (1-2 строки)
- Ссылки (продакшн, VK, и т.д.)
- Сервер (IP, SSH, таблица компонентов)
- Стек технологий (кратко, по строке на компонент)
- Деплой (1-2 строки + ссылка на docs/deploy.md)
- Локальная разработка (команды)
- Логи (команды для просмотра)
- Troubleshooting (частые проблемы)

**DETAILED (выносится в docs/)** — детальная информация, которая нужна только при работе с конкретным компонентом:
- Подробная структура файлов
- API эндпоинты
- Схема БД
- Детали фич
- Архитектура компонентов

### Шаг 3: Реорганизация (только при первом запуске)

#### 3a. Создать `docs/` если не существует

```bash
mkdir -p docs
```

#### 3b. Создать/обновить файлы в docs/

Для каждого крупного блока детальной информации создай отдельный файл в `docs/`.
Типичная структура:
- `docs/web.md` — веб-приложение (компоненты, фичи, localStorage)
- `docs/api.md` — API (эндпоинты, БД, скрипты)
- `docs/bot.md` — телеграм-бот (конфигурация, автопубликация)
- `docs/deploy.md` — деплой (CI/CD, ручной деплой, логи)
- `docs/audio.md` — архитектура аудио (если есть)
- другие файлы по необходимости

Если файл уже существует в `docs/` — проверь его содержимое и обнови при необходимости, не перезаписывай без причины.

#### 3c. Переписать CLAUDE.md

Новый формат CLAUDE.md:

```markdown
# [Название проекта]

<!-- DOCS: При изменении документации используй /docs — не редактируй CLAUDE.md вручную -->

<!-- ESSENTIAL:START — Ядро проекта. Обновлять через /docs, не трогать вручную -->

[Краткое описание проекта — 1-2 предложения]

[Ссылки, сервер, стек, деплой, локальная разработка, логи, troubleshooting — КРАТКО]

<!-- ESSENTIAL:END -->

## Подробная документация

- [Web App](docs/web.md) — описание
- [API](docs/api.md) — описание
- [и т.д.]
```

**КРИТИЧЕСКИ ВАЖНО для блока ESSENTIAL:**
- Между тегами `<!-- ESSENTIAL:START -->` и `<!-- ESSENTIAL:END -->` — ТОЛЬКО то, что нужно при каждой сессии
- Без лишних деталей — только самое важное, компактно
- Детали — в docs/ файлах со ссылками

### Шаг 4: Верификация актуальности

Для КАЖДОГО утверждения в документации проверь:

1. **Файловая структура** — используй Glob чтобы проверить что указанные пути и файлы существуют
2. **Зависимости** — проверь package.json, requirements.txt и т.д. на соответствие указанному стеку
3. **Команды** — проверь что указанные npm scripts / команды существуют
4. **CI/CD** — проверь workflow файлы на соответствие описанию деплоя
5. **Конфигурация** — проверь порты, пути, сервисы

Для каждого несоответствия:
- Если можно определить правильное значение из кода — исправь документацию
- Если непонятно — спроси пользователя через `AskUserQuestion`

### Шаг 5: Отчёт

Покажи пользователю:
1. Что было изменено (список файлов)
2. Что было проверено и актуально
3. Что было исправлено (если были неточности)
4. Вопросы (если остались неопределённости)

Затем через `AskUserQuestion` предложи:
- **"Закоммитить"** — `git add CLAUDE.md docs/ && git commit -m "docs: reorganize CLAUDE.md documentation"`
- **"Пока не надо"** — оставить изменения локально

## Правила обновления (повторные запуски)

При повторном запуске скилл НЕ должен:
- Перезаписывать весь CLAUDE.md
- Перезаписывать docs/ файлы без причины
- Трогать блок ESSENTIAL без реальных изменений

Скилл ДОЛЖЕН:
- Проверить блок ESSENTIAL на актуальность (Шаг 4)
- Проверить docs/ файлы на актуальность (Шаг 4)
- Добавить новую информацию если она появилась (новые компоненты, эндпоинты, и т.д.)
- Удалить неактуальную информацию если что-то было удалено из кода
- Обновить только те секции, где есть реальные расхождения с кодом

## Что НЕ входит в docs/

- README.md — это для пользователей GitHub, не для Claude
- Файлы в .claude/ — это конфиг Claude Code
- Тесты, миграции, скрипты — это код, не документация

## CRITICAL RULES

- ВСЕГДА читай код перед обновлением документации — никогда не пиши наугад
- Блок ESSENTIAL должен быть максимально компактным — каждая строка экономит контекст
- Ссылки на docs/ файлы ВСЕГДА должны быть относительными
- Не добавляй в документацию секреты, токены, пароли
- Если находишь секреты в существующей документации — предупреди пользователя и предложи удалить
- Язык документации: такой же как в существующем CLAUDE.md (обычно русский или английский)
